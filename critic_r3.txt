METHOD
  Every program below was authored by me, armed on a spawned rig via
  ProgramRunner.Init/program (the VerbBench pattern), and sampled at the
  physics rate (0.02 s).  Two rigs were used:
    RIG-S  the 20-part spinner rig from the session handover (core, spinner,
           4 wheels, compass, dmgbus, wallsensor).  NOTE: its wheel pairs are
           mounted at DIFFERENT rotations (front pair rot 90, rear pair rot 0)

    RIG-C  a mechanically consistent 10-part rig, 4 aligned wheels
           (the VerbBench BODY shape).
  Every negative result has a control leg, marked CONTROL.

R1  BLOCKER - THE WEAPON LATCH NEVER RELEASES A PREEMPTED ACTUATOR STEP.
    Program (critic_r3_a.txt, A1):
        hat 0  WHEN hp < G          : MOVE 50% FOR 1.0 s        (G flipped by me)
        hat 1  WHEN always          : RUN WEAPON 90% FOR 5.0 s
        Validate: OK.
    Sequence: G false, so hat 1 runs.  At t=1.5 s I set G true so hat 0 preempts.
    MEASURED (rig RIG-S, one actuator):
        t=1.2  hat=1  actFire=True   spinner rate 49.5
        t=1.8  hat=0  actFire=True   rate 63.5     <- preempted
        t=7.8  hat=0  actFire=True   rate 73.5     <- 2.8 s PAST its own 5 s
        t=8.8  hat=1  actFire=True
    CONTROL (A1c, identical step, never preempted):
        t=1.0 actFire=True ; t=5.6 actFire=False.  Correct.
    WHAT THE PROGRAM SAYS: run the weapon for five seconds, then stop.
    WHAT HAPPENS: the weapon runs forever.
    CODE PATH: ProgramRunner.ExitStep is the ONLY caller of ZeroMotor()/
    SetFire(b,false), and it only runs when StepDone() returns true.  A
    preemption goes TriggerEval -> StartHat -> ZeroDrive(), and ZeroDrive was
    changed in R2 to leave actFire alone.  Before R2, StartHat's ZeroChannels
    cleaned this up.  The same hole exists for FIRE n CYCLES and for
    SET/RUN on PPart.Actuator.  A preempted actuator step leaks its channel
    permanently.
    FIX SHAPE: on StartHat/ReleaseHat, run ExitStep for the step that was in
    flight (or record which actuator channels the in-flight step owns and
    release only those), instead of leaking the whole latch.

R2  MAJOR - THE WEAPON KEEPS SPINNING WHEN NO HAT IS TRUE AT ALL.
    Program (A2):
        hat 0  WHEN hp < G : WEAPON ON ; MOVE 40% FOR 1.0 s     (only hat)
    I flip G false at t=1.2 s, so nothing in the program is true any more.
    MEASURED:
        t=1.2  hat=0   actFire=True
        t=3.2  hat=-1  actFire=True  rate 73.5  maxWheelCmd 0.00
        t=7.2  hat=-1  actFire=True  rate 73.5
    The robot sits perfectly still with the weapon at full speed for the rest
    of the fight.  The player wrote a program that arms the weapon only inside
    one conditional hat; there is no way to express -stop when that hat stops-
    except by adding a catch-all WEAPON OFF hat, which nothing tells them to do.
    COST: a continuously latched weapon drains the reserve at about 0.005 of
    PowerFrac per second (measured E2: 0.79 -> 0.69 over 19 s of spin).  Over a
    60-90 s fight that is 30-45% of the reserve spent on a weapon the program
    never asked to keep running - a real, if not fatal, difficulty shift.
    CONTROL (A3): a hat that says WEAPON ON, WAIT 1.5, STOP ALL, WAIT 3
    correctly reads actFire=True at t=1.0 and actFire=False at t=2.2.  STOP ALL
    and death still clear the latch as designed.

    1.00 AND THE RETREAT HAT CAN NEVER FIRE.
    Program (critic_r3_h.txt, H4):
        hat 0  WHEN hp < 35%  : MOVE BACKWARD 70% FOR 1.0 s     (RETREAT)
        hat 1  WHEN always    : MOVE FORWARD 25% FOR 1.0 s      (CHARGE)

R5  THE STALL ESCAPE - I could not make it fire on legitimate slow progress,
    but it IS converting hangs into SILENT WRONG ANSWERS.
    Controls first (critic_r3_b.txt):
      MOVE 25% FOR 3 ROUNDS   ran 5.36 s, 3.45 m, 3.04/3 rounds  - completed on
        rounds, NOT stalled, even though its first 2 s averaged only 0.243 m/s
        (the stall floor is 0.15 m per 1.2 s = 0.125 m/s, so it is close).
      MOVE 40% FOR 3 ROUNDS   ran 2.26 s, 3.32 m, 3.07/3 rounds  - correct.
      MOVE 70% FOR 3 ROUNDS driven into a wall: ended at 1.94 s with 0.00/3
        rounds - a correct escape, 1.2 s after the machine actually stopped.
      Timed steps are never stall-checked at all (StepDone returns on b.dur),
        so a slow MOVE 15% FOR 5 s cannot be truncated.  Good.
    But on RIG-S:
      TURN BY 15 deg  -> ended after 1.22 s having turned 0.0 deg
      TURN BY 30 deg  -> ended after 1.66 s having turned 14.0 deg
      SIDE TO WALL / FRONT from 24.1 deg -> ended after 1.22 s at 16.8 deg

    not the same event as a step that ends because it finished, and the runner
    does not distinguish them - which also means a FaceSide that gave up
    silently satisfies its own 8 deg contract as far as the sequence is
    concerned.

BLOCKER 1 - F6 CONSTRUCTED AND MEASURED: A FOREVER WHOSE ONLY BLOCKING STEP IS
            BEHIND A FALSE IF LOCKS OUT EVERY LOWER HAT, PERMANENTLY.
    Program (critic_r3_d.txt, D1):
        hat 0  PATROL  WHEN always
                 FOREVER
                   IF hp < -1          (a condition that is simply false)
                     MOVE 70% FOR 1.0 s
                   END IF
                 END
        hat 1  SAFETY  WHEN always
                 MOVE 85% FOR 1.0 s
    Validate(partIds) returns null.  The canvas accepts it, SAVE accepts it,
    LOAD TO ROBOT accepts it.
    MEASURED over 8.0 s (401 physics steps):
        wheel command live         0 %          (never non-zero, once)
        hat 0 in charge          392 steps
        hat 1 in charge            0 steps      <- the safety hat never runs
        distance moved          0.00 m
        average frame           20.0 ms         (no perf hazard - it is silent)
    CONTROL - the same program with the IF made true, 5.0 s:
        wheel command live        96 %
        hat 0 in charge          242 steps
        distance moved          8.59 m
    WHY: Validate marks a loop as having a blocking step if ANY b.Blocking step
    appears while the loop is open, without caring that the step is inside a
    false IF branch.  At run time Advance walks FOREVER -> IF(false) ->
    SkipFromIf -> END -> back to FOREVER, three instants per lap, burns the
    64-instant budget and yields, forever.  TriggerEval sees InForever() true
    but the hat WHEN is still true, so it never releases; and preemption is
    -strictly higher hats only-, so every hat BELOW is starved.  A player who
    puts a WALL! or FLIPPED! safety hat under a patrol hat gets a robot that
    stands motionless for the whole fight.
    FIX SHAPE: the run-time side is the real fix - if a FOREVER lap completes
    with no blocking step executed, treat the hat as finished (release it) so
    lower hats get a turn.  A static check can only ever be a heuristic here
    because the IF is data-dependent.

BLOCKER 2 - THE WALL LIMIT CYCLE IS REAL AND IT IS THE WHOLE ARENA.
    (R2 major 2, confirmed and re-characterised.  critic_r3_j.txt.)
    Program: one hat, WHEN always, MOVE AWAY FROM WALL 80% (HOLD / SET flavour).
    Rig RIG-C, started 2.5 m from the +Z wall with that wall dead ahead.
    MEASURED, 11 s, wheel commands in brackets:
        t= 0.0  d=2.52  bear= -21  w=[ 0.00, 0.00, 0.00, 0.00]  v=0.00  z= 4.5
        t= 1.5  d=6.80  bear=-178  w=[ 0.73, 0.87, 0.73, 0.87]  v=7.49  z=-0.4
        t= 3.0  d=3.42  bear=-179  w=[ 0.77, 0.83, 0.77, 0.83]  v=3.10  z=-3.5
        t= 4.5  d=2.52  bear=  -7  w=[-0.55,-1.00,-0.55,-1.00]  v=2.84  z= 4.5
        t= 6.0  d=5.73  bear=  -4  w=[-0.65,-0.95,-0.65,-0.95]  v=7.18  z= 1.1
        t= 7.5  d=1.12  bear=-173  w=[ 0.56, 1.00, 0.56, 1.00]  v=1.37  z=-5.9
        t= 9.0  d=4.42  bear=   1  w=[-0.84,-0.76,-0.84,-0.76]  v=6.96  z= 2.8
        t=10.5  d=3.43  bear=   0  w=[-0.81,-0.79,-0.81,-0.79]  v=5.84  z= 3.3
        SUMMARY: wallDist 1.02 .. 6.91 m, five 180-degree bearing flips, peak
        speed 7.5 m/s in a 14 m arena.
    Second leg, same order but started with the wall ASTERN: wallDist
    1.02 .. 6.89 m, six flips, peak 9.16 m/s.
    Third leg, started at the arena CENTRE: the robot barely translates
    (wallDist 4.67 .. 6.98) but the wheels chatter at full opposite lock -
    w=[0.95,-1.00,...] on one sample and w=[-0.94,1.00,...] the next - ten
    >90-degree bearing flips in 11 s.  On rig RIG-S the same centre test gave
    40 flips in 18 s while the robot did not move at all.
    WHAT THE PROGRAM SAYS: keep away from the walls.
    WHAT HAPPENS: the robot ping-pongs between the two opposite walls forever,
    coming within 1.02 m of a wall - closer than the StarterKit WALL! hat
    threshold of 1.2 m that exists to prevent exactly this.
    WHY, precisely:
      (a) SensorBus.ReadWall reports only the SINGLE nearest of four planes,
          with no memory and no hysteresis.  Crossing the mid-line swaps the
          plane and the bearing jumps 180 degrees (or 90, for a side wall).
      (b) RelDrive computes drive = -cos(bearing), which is smooth IN THE
          BEARING - but the bearing is a discontinuous function of POSITION,
          so the drive command flips sign at full magnitude.
      (c) AWAY has no set point.  -Increase the distance- is unsatisfiable in a
          bounded arena, so the controller never converges and never slows.
      (d) There is no brake (see MAJOR 5), so each half-cycle overshoots.
    WHAT A GOOD FIX NEEDS - all four, not one:
      1. A TARGET CLEARANCE, not an unbounded objective.  AWAY FROM WALL should
         mean -open the range to at least C metres, then stop- (C tied to the
         hat threshold, e.g. 2.0 m against a 1.2 m trigger).  Then the verb can
         terminate and the hat can release.
      2. A CONTINUOUS FIELD instead of nearest-plane-only.  Sum a repulsion
         vector over all four planes (1/d or 1/d^2 weighted).  That vector is
         continuous everywhere including the mid-line and it has no antipode.
         SensorBus already comments that the roster AI has such a repulsion
         query - use the same one, and expose the VECTOR, not one bearing.
      3. If (2) is too big, at minimum PLANE HYSTERESIS in ReadWall: keep the
         plane you are reporting until another is closer by a margin (0.5 m),
         so a mid-line crossing cannot flip the bearing at all.
      4. A SPEED GOVERNOR on the retreat.  7.5 m/s across a 14 m arena means
         the robot is at the opposite wall 0.9 s after leaving this one.

MAJOR 3 - SIDE TO <target> OVERSHOOTS ITS OWN 8-DEGREE CONTRACT AND STOPS,
          ON A GOOD RIG.
    Program: one hat, WHEN always, SIDE TO WALL / FRONT.
    MEASURED on RIG-C (critic_r3_i.txt):
        from -169.9 deg : ran 1.36 s, ended at bearing  32.2 deg
        from   49.2 deg : ran 0.60 s, ended at bearing -18.2 deg
    MEASURED on RIG-S (critic_r3_c.txt):
        from   24.1 deg : ran 1.22 s, ended at bearing  16.8 deg (stalled out)
        from -177.1 deg : ran 2.76 s, ended at bearing  -4.8 deg  (correct)
    The verb declares FACE_TOL = 8 deg.  Three of the four legs finish outside
    it, and two of them finish on the FAR SIDE of the target - the robot swung
    past and kept going.  Cause: StepDone declares success the instant
    |err| < 8, then ExitStep calls ZeroWheels and the machine coasts on its
    angular momentum (RIG-C pivots at up to 156 deg/s at 65% power, and
    wallBearingDeg only refreshes at 20 Hz, so one sensor frame is already
    7-8 degrees wide).  There is no braking phase and no dead-band.
    WHY NO BENCH CAUGHT IT: VerbBench asserts err1 < 35 deg, four times the
    verb contract.  16.8 and 32.2 and 18.2 all pass.
    FIX SHAPE: brake (command the opposite sign for a step or two, or scale the
    pivot power by remaining error with a much lower floor than 0.20), and
    assert the verb contract in the bench, not a number four times looser.

SECTION 3 - THE PROGRAMCANVAS PATH, END TO END
================================================================================
    (critic_r3_g.txt.  The canvas is not in the scene at rest - MobileBuilderUI
    mounts it on the career-only PROGRAM panel - so I mounted a ProgramCanvas
    on the live mobile_builder_canvas exactly the way MobileBuilderUI does
    (AddComponent + Init(bm)), then drove it by invoking the real Button
    onClick of the real chips, by name, with a frame between taps.  The
    player-s career data was snapshotted and restored, and autosave was off for
    the duration.)

  TAPS PERFORMED, and what the canvas produced after each:
    + HAT               -> hat 0, WHEN ALWAYS, [MOVE FWD 70% 1.0 s]
    + BLOCK             -> block 1 = MOVE FWD 70% 1.0 s
    op chip x3          -> block 1 cycled Move -> TurnLR -> TurnBy -> Weapon ON
    power chip x2       -> block 0 arg 70 -> 85 -> 100
    duration chip x1    -> block 0 dur 1.0 -> 1.5
    WHEN kind chip x1   -> Always -> ENEMY RANGE, value reset to 0.5
    WHEN value chip x1  -> 0.5 -> 1
    + REPEAT            -> [REPEAT 3 ; MOVE FWD 70% 1.0 s ; END]

  DRAWN PROGRAM:
    H0 WHEN EnemyRange > 1
       0 Move   arg=100 dur=1.5
       1 Weapon arg=100
       2 Repeat arg=3
       3 Move   arg=70  dur=1
       4 End

  LOAD TO ROBOT -> status: loaded to spinner1 (1 hats, 5 blocks) - TEST DRIVE
  -> AUTO to watch it.  Robot JSON 643 bytes.

  STORED ON THE ROBOT (RobotProgram.FromJson of what was written): identical in
  every field that the runner reads - op, part, idx, arg, dur, rounds, target,
  hat order, WHEN terms.  ARMED PROGRAM after BackToBuild + StartTest:
  identical again, and bm.testRunner was non-null.

  >>> VERDICT: the program that runs IS the program that was drawn.  The
      canvas -> JSON -> stable robot -> ProgramRunner path is faithful.  This
      was the highest-value untested surface and it is clean.

  The only difference across the round trip is an artefact worth knowing about
  but not worth fixing: JsonUtility never writes null for a nested serializable
  class, so every block comes back with cond = {Always, Less, 0} instead of
  null.  The runner only reads b.cond on POp.If, and Validate only requires it
  to be non-null on POp.If, so it is inert.  It does mean Validate can never
  report -IF without a condition- for a program that has been saved once.

  THREE CANVAS DEFECTS FOUND WHILE DRIVING IT (none change what a valid program
  does at run time):
    C1  Cycling a WHEN chip off ALWAYS sets the VALUE from the new kind but
        leaves the COMPARATOR at the ALWAYS default, which is GREATER.  So one
        tap turns WHEN ALWAYS into WHEN ENEMY RANGE > 0.5, and a player reaching
        for HP FRAC gets WHEN HP > 0.1, which is true always.  The first tap on
        every new condition produces a hat that fires all the time.  A sensible
        default per kind (ranges and hp want <, PartsLost wants >) would remove
        a whole class of -my safety hat never stops firing- confusion.
    C2  CycleOp sets b.part = PPart.AllWheels for EVERY op, including WEAPON and
        FIRE.  Inert at run time (the runner ignores part for POp.Weapon) but
        the data is wrong and Lint reasons about part.
    C3  CycleOp resets b.arg to a positive default, so cycling a block away from
        MOVE BACKWARD and back again silently loses the direction the player
        chose.

SECTION 5 - SUSPECTED BUT NOT MEASURED
================================================================================
  S1  A rounds-mode MOVE TOWARD/AWAY can satisfy its round count by PIVOTING.
      RoundsDelta sums |WheelRollSpeed| over all channels, and a pure pivot has
      non-zero roll speed on every wheel with opposite signs.  So MOVE TOWARD
      ENEMY FOR 3 ROUNDS should be satisfiable without approaching at all.
      Code read; I ran out of time to build the geometry for it.
  S2  Damage-balance impact of the weapon latch.  R2 measured the spinner duty
      going from 9% to 100% of a fight.  I measured the power cost of a latched
      weapon (about 0.005 PowerFrac/s) but did NOT run paired fights against a
      roster opponent, so I cannot say whether tier difficulty has actually
      moved.  That needs a scripted best-of-N against a fixed opponent, before
      and after.
  S3  ApplyChannels sets drive.directWheelCmd = true on every physics step even
      when activeHat < 0 and every channel is zero.  For a robot whose
      controlSource is Program that is presumably intended, but it means an
      idle program actively holds the wheels at zero rather than releasing
      them; whether anything else wants the drive in that window I did not test.
  S4  The 5 Hz TriggerEval and the 20 Hz wall / 10 Hz compass refresh are not
      phase-locked.  A hat whose WHEN sits exactly on a threshold will see the
      same sensor sample for two or four consecutive evals.  I saw no
      misbehaviour from it, but it is the kind of thing that makes a hat look
      sticky.
  S5  I never tested two programmed robots fighting each other (a robot pushing
      another robot was the specific slow-progress case I was asked about).
      Every rig I could spawn through BuilderManager.StartTest is alone in the
      arena with a ram dummy; setting up a second programmed CompoundRobot was
      beyond what I could reach without touching FightManager.  The pushing
      case for the stall watch is therefore UNTESTED - it is the one gap I
      would close first.
