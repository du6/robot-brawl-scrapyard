## 3. The cold-start deadlock, and why it matters more than it sounds

A validated robot was ACTIVE, correctly categorised, visible to its OWNER —
and invisible to everyone else, because ratings rows were only created by the
first FIGHT and the leaderboard reads `ratings`. Two players could both enlist
and neither could see the other, so neither could issue the first challenge,
so no rating was ever created. League nights could not break the tie either:
they draw from the top 8 of `ratings`.

**The ladder had no way to begin, and every bench was green.** It was found by
working the first real job in the cloud and then looking at the board.

Validation now creates the placement row, `ON CONFLICT DO NOTHING` so
re-uploading never resets an earned rating.

## 4. Four defects that only a real run could find

1. **The worker could not read its own payloads.** Blobs moved behind
   `/v1/blobs` with §1.3 auth and nothing updated the fetcher — 401, and the
   worker correctly declined to judge what it could not read, so uploads sat
   PENDING until the reaper rejected robots that were never bad. The key is
   now sent **same-origin only**, compared on parsed scheme+host+port: the
   payload URL comes from a server response, so `StartsWith` would hand the
   shared secret to `rb-api.example.com.evil.test`.
2. **The server build stripped its shaders.** Dedicated Server Optimizations
   removes shaders, and the real code path builds render materials while
   constructing a robot → `ArgumentNullException` → every job left for retry.
   The container looked healthy throughout. Fixed in the BUILD, not the game
   code: §5.2 exists so there is one implementation and zero drift.
3. **The scheduler silently did nothing** without `roles/run.invoker` on the
   job. No error anywhere obvious; three forced runs produced no execution.
4. **A claim had no kind filter**, so a worker claimed work it could not run,
   refused it, and burned an attempt. Three of those FAIL a good job — and a
   failed VALIDATE now rejects the player's robot.

## 5. ⚠ THE CAREER SAVE WAS OVERWRITTEN. READ THIS BEFORE RUNNING BENCHES.

I ran `HazardBench`, `CareerBench` and `TouchSmoke` **in the same frame**.
They all drive the builder, the arena and `Career.Data`, and `BuildArena()` is
not idempotent. The save came back with 65 fights where there were 11, 24 wins
where there were 8, 218,361 scrap where there were 6,513, and the medals and
stable **wiped**.

Restored byte-identical from `career_backups/pre_stalegreen_20260810_010747.json`.
The damaged file is kept as `DAMAGED_by_concurrent_bench_run_20260810.json`.

**The mechanism was a real defect, and it was two.** Those benches ended with
`Career.autosave = true` — not a restore, an assumption — so each one ENABLED
writes on its way out. Fixing that to restore the captured value is correct
and would not have prevented this: all three captured `true`. A save/restore
of one global is not safe when two holders overlap.

`Career.SuspendAutosave()` is now a **counted** hold; autosave returns only
when the last holder releases, and the count floors at zero. Proven by
re-running the exact combination — the save came back byte-identical.

**The operational rule still stands: run career-touching benches ONE AT A
TIME.** The guard protects the save; it does not make concurrent runs valid.
Measured: HazardBench 7/7 fail concurrently, **23/23 alone**. TouchSmoke
17 pass/12 fail concurrently, **29/29 alone**.

## 6. The sensor palette was unreachable

Four parts — Tilt sensor, Wall sensor, Trap sensor, Damage bus — sat sliced in
half at the bottom of the build dock with no way to scroll to them. The whole
sensor palette, in the shipped single-player builder.

Cell WIDTH has been derived from the viewport since R6; HEIGHT stayed pinned
to a touch row, which held only while the rows happened to fit. The sensor
palette took the catalogue to 25 parts and FOUR rows, and the 0.68-of-screen
dock cap — which by design has the last word — handed back less than the grid
needed.

I got the fix wrong twice with correct arithmetic, both times by running it
when the inputs did not exist yet. **A fix that changes the measurement by
exactly zero is usually not running, not wrong.**
