# The gusset holds ×4 — shipped, measured, and what it did NOT do

**2026-08-18.** owen: *"let's increase the gusset's adhesive strength.
basically if two parts are joint with gusset in between, it's very hard to
tear them apart."*

`BuilderManager.GUSSET_SEAM_MULT` **1.5 → 4.0**. Nothing else changed: not
`GUSSET_KG`, not the stock rules, not the per-joint face mask, not
`BREAK_K`. This is a strength change to one constant and it is deliberately
the only thing in the commit that moves.

The prediction was written before the constant moved and is committed
unedited as `docs/_gusset_prediction_20260819.md` (house rule 6). It is only
worth something because it cannot be revised after the fact. Scored below.

---

## 1. What was measured, and how

Not through a bench — **no bench in this project has ever measured a seam
threshold**, which is itself worth knowing before trusting the change. Two
probes were run over the bridge in edit mode, each spawning two robots from
the SAME recipe and comparing `CompoundRobot.edges[].threshold` label by
label.

### Probe A — the hardened enemy (every non-wheel face gusseted)

`EnemyRoster.Recipe("brawler", pal, "Steel", hardened: true)` sets
`gussetFaces = 63` on every non-wheel part, so every seam is reinforced.

```
edges compared: x4 = 11   unchanged = 0   OTHER = 0     (11 edges either side)
  core_0↔chassis_1     900.0 ->  3600     x4
  core_0↔chassis_2     900.0 ->  3600     x4
  core_0↔engine_3      900.0 ->  3600     x4
  core_0↔battery_4     900.0 ->  3600     x4
  core_0↔gyro_5        900.0 ->  3600     x4
  chassis_1↔engine_3  4500.0 -> 18000     x4
```

Every seam scaled by **exactly 4.000**, none by anything else. Note the two
rows are different absolute thresholds (900 is a one-socket seam, 4500 is
five) and both scale identically — the gusset multiplies, it does not floor.

### Probe B — the control, and it is the leg that matters

Probe A cannot tell a per-joint multiplier from a global one: if the change
had leaked into every seam in the game, Probe A would look identical.

So: the same recipe, **exactly one part gusseted** (`chassis_1`, all six
faces), everything else untouched.

```
CONTROL: seams touching the gusseted part that moved x4 = 4
         seams elsewhere that did NOT move              = 7
         WRONG                                          = 0
```

Four seams touch that chassis and all four moved; the other seven did not
move at all. **The gusset is still per-joint.** Hard rule 4 exists for
exactly this: the ×4 result on its own proves nothing without the leg that
could have failed.

## 3. A finding that has nothing to do with the gusset

`DisarmBench` was started on a freshly opened `Main.unity` and returned
**0 pass, 1 fail** in under a second:

```
FAIL  BuilderManager in scene
```

**`Main.unity` contains no `BuilderManager`.** The only thing that ever
creates one is `StartCareer()`, which is reachable only by a click on the
title screen. So every fight-running bench in this project —
`DisarmBench`, `MatrixBench`, `LadderSweepBench`, `OpeningBench`,
`CareerBench` — is unrunnable from a fresh scene unless a human has first
clicked *Start* by hand.

This is the **same defect, in a second place**, that stopped the worker
container booting earlier today (`WorkerBootstrap` launched `WorkerHost`
into a scene with no builder and exited 3). One missing object, two
subsystems, both of which looked like something else: the worker read as a
broken image, and the bench reads as a bench that ran and failed.

⚠ And it is a **`passed == 0` result**, the exact shape `CLAUDE.md` warns
about. "1 failed" at least says something is wrong; a bench that guarded
differently would have skipped and read as green.

Worked around here by creating a headless `BuilderManager` before the run,
which is what `WorkerBootstrap` now does in the product. **Nothing has been
changed in the benches** — naming this is worth more than papering over it,
and the fix belongs with whoever decides whether the scene should carry one.

## 4. Prediction 4, and the bench that cannot answer it

`DisarmBench` was run to completion: **32 pass, 0 fail** — the documented
count, reproduced. Its headline is unchanged from the committed baseline:

```
bouts run: 30 over 2 seeds x 15 pairings
bouts ending with BOTH sides disarmed:   13/30  (43%)
bouts ending with EITHER side disarmed:  26/30  (87%)
```

It would be very easy — and wrong — to write that down as *"×4 moved the
disarm rate by zero bouts, exactly as predicted."*

**The fixture has no gussets.** `DisarmBench` loads `VerbBench.ARMED`, and
that snapshot string carries **not one `|G:` mark**: `grep -c '|G:'` over it
returns 0. `GUSSET_SEAM_MULT` is applied only where a mating face carries
the gusset bit, so on this fixture the constant is never read. The 43% could
not have moved whatever the value.

So prediction 4 is **not confirmed and not refuted — it is untested**, and
the real finding is one level up:

⚠ **No bench in this project fights gusseted robots.** `DisarmBench`,
`MatrixBench`, `OpeningBench` and `LadderSweepBench` all descend from the
same ungusseted rig. The only gusseted machines in the game are the
HARDENED enemies in `CareerBench`, which is a balance harness whose bands
are already coin flips at its shipped sample size. A constant that governs
how hard it is to tear a robot apart has **no fight-level cover at all**,
and at ×1.5 that was easy not to notice.

Two smaller notes from the same run, neither attributable to this change:
the non-weapon destruction count moved 90 → 99 and the wreck/shed split
9/18 → 10/17 against a baseline committed nine days ago, across which much
else changed. Read them as drift, not as signal.

## 5. What is NOT measured

* **Prediction 4 — the mutual-disarm rate under gussets.** See §4. Closing
  it needs a fixture with `|G:` marks on it, which does not exist yet.
* **Career balance.** `CareerBench` bands will move because hardened enemies
  are now four times harder to disassemble, and at its shipped sample size
  three of eleven verdicts are already coin flips
  (`CareerBench_Sample_Size_2026-08-10.md`). Re-running it at `SampleMul`
  ≥ 3 is the only way to say anything true about difficulty, and that is
  owen's call because it is a tuning question, not a correctness one.
* **The player's own experience of the change.** Nobody has built a gusseted
  robot and hit it with a hammer.
